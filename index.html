01 · 为什么

为什么要做消费记忆？

记账解决的是“记录发生了什么”。真正长期有价值的问题，是消费发生之后，信息有没有被记住、理解和重新调用。

传统记账

记录一笔交易

2026-09-18 · 玩具 → 积木 · ¥199。信息被准确保存，但它仍然只是一个时间切片。

消费记忆

理解一段消费经历

什么时候买的？后来有没有用？是否少用、退货、闲置？这些后续事实可以继续成为用户自己的长期记忆。

“我想知道自己买过什么、花了多少、值不值——不用一年一年翻，直接问就行。”
项目中的核心任务定义
02 · 产品机会

为什么不继续卷 AI 自动记账？

语音、OCR、自动分类、自然语言查询都可以提升记录效率，但只在“记得更快”上竞争，产品差异会越来越弱。

传统记账

记录

钱 → 记录 → 统计。核心目标是把账记下来。

AI 记账

自动化

钱 → 理解 → 自动记录 → 统计。降低输入成本，但仍围绕交易。

本项目

记住

钱 → 消费 → 记录 → 记忆 → 追踪 → 行为理解。把“交易”变成长期可调用的消费记忆。

产品定位
让竞争维度从 更高效地记录 转向 更有意义地记住。
这不是在给记账增加更多入口，而是在重新定义“记账之后还能发生什么”。
03 · 产品决策

产品决策：意图优先，而不是功能菜单

用户通常不会想着“我要打开记账功能”，而是直接表达任务。Agent 负责把自然语言转化成可执行的工作流。

用户表达“咖啡35”
理解意图记账 / 查询 / 修正 / 分析
读取上下文历史记录与会话上下文
选择工具检索 / 更新 / 调度
判断边界置信度 / 歧义
执行或询问执行 / 澄清 / 确认
最小闭环

记账 → 记忆 → 检索 → 追踪 → 洞察

把 P0 主线收敛成一条可验证的纵向闭环，而不是把所有 AI 能力都放进最小版本。

运行形态

Demo 阶段选择飞书 CUI

低触达摩擦，原生承载语音、图片、文件和群共享；复杂分析展示可以通过文档辅助。

04 · Agent 设计

Agent 不是一个聊天框

Agent 能力从具体任务中的理解、推理、规划、记忆和工具缺口反推，而不是从“用了哪个模型”来定义。

AGT-01 · 意图理解与编排理解语音 / 文字 / 图片 / 文件，拆分多笔消费，分类并生成待确认结果。
AGT-02 · 消费记忆检索从消费数据库检索相关消费，并结合上下文组织答案。
AGT-03 · 主动追踪与状态管理基于触发条件进入追踪状态，发送主动消息并处理回答与不回答。
AGT-04 · 模式分析与边界控制检查数据充分性，再决定是否允许进行模式推断。
AGT-05 · 上下文与指代消解处理“那个 / 那笔 / 上次买的”，并根据候选结果决定直接执行还是请求用户澄清。

05 · 信任与边界

当 Agent 不确定时怎么办？

这是整个项目中最核心的 Agent 交互问题之一：不猜、不越权、保留用户最终控制权。

1 个候选

唯一匹配
继续执行。Agent 有足够证据定位到目标。

≥2 个候选

多候选
展示候选并请求用户选择，不擅自猜测。

0 个候选

无匹配
停止自动执行，请用户补充信息。

一个很典型的 Agent 问题
“把那个改成在用。”
Agent 会按时间、品类 / 关键词、金额、商户、上下文等维度定位记录。最终得到的不是一个普通“搜索结果”，而是一个需要考虑不确定性的产品决策。
人在回路中

高风险动作不交给 Agent 猜

未经确认不入账；删除与恢复有二次确认；多候选需要用户选择。

证据优先

置信度最终要落到行为

不是为了展示一个漂亮百分比，而是决定“执行、确认还是澄清”。

08 · Agent 评测

评测不是「跑一遍测试」，是把判断变成可判定的标准

这一节是评测体系的设计、两轮实测结果，以及我自己推翻自己结论的那一次。设计判断要能被验证，前提是它得有对错；而「对错」必须独立于被测实现——否则测的是自己抄的答案。

01

先把「对」写下来：正确行为与判定规则分开

GT · 正确行为被测系统在给定输入下应该展现的输出与行为
Oracle · 判定规则试跑之后用来自动或人工判定通过或差异的规则
允许变化GT 允许的合理变体——不算差异
禁止行为绝对不能做的事，出现即为红线违规
示例 · AC-01 记账主路径
输入：「咖啡35」

正确行为（GT）
回复卡片显示 ¥35 · 一级=餐饮 · 二级=咖啡
含「确认入账」「修正」按钮
记录处于待确认状态，未写入数据库

允许变化
二级品类名可不同（咖啡 / 咖啡豆 同义）
卡片布局可不同 · 语音与文字路径结果可一致

禁止行为
未经确认直接入账（RED-05）· 编造金额
无金额输入时强行分配 · 拟造不存在的处理步骤
「允许变化」这一段最关键——它挡住了评测最常见的失败模式：把「文案不同」判成「功能失败」。
02

判据要能被核，也要让被测系统读不到

判据出处可核

每条断言都指回规格条款

232 条机器断言与 52 条人工判据，每一条都标注它来自哪条规格条款，由脚本逐条校验：题号存在、条款编号不越界、观察面名真实。284 条引用全部指向真实条款，并作为 CI 闸门——判据来源一旦对不上，构建直接失败。

四平面隔离

把答案从运行包里搬出去

运行输入、评测管控、构建、证据分成四个平面。期望金额、标准答案、案例编号映射全部放在「评测管控」平面，该平面对被测系统标记为不可读。隔离不靠文档声明，靠每次构建都跑检测器。

平面装什么被测系统能否读取
运行输入测试输入、前置状态、原始数据可以
评测管控期望值、标准答案、案例编号映射不可以
构建运行包与发布物按发布物走
证据试跑记录与权威状态读回不参与推理
03

五个观察面，四态判定

结果用户目标是否完成
对话用户实际看到了什么
过程内部发生了什么：检索、匹配、工具调用
状态权威状态如何变化
真实动作外部动作是否真实发生
总判定规则

四态，不是两态

一致 observed_match / 有差异但没踩红线 observed_gap / 前提阻断无法观察 blocked / 本轮没看 not_evaluated。

全部一致才算通过；有差异记为 Bad Case；踩红线直接判负；受阻不算通过——把「没看见」当成「没问题」，是评测里最容易犯的错。

红线单独统计，不参与平均。一个平均分能盖住的数据损坏，比没有分数更危险。

05

然后我没有相信这份绿灯

12 / 12 全 Pass、红线 5 / 5 —— 我判定这份结论失效，重建隔离后重跑。
触发这次自查的不是试跑失败，而是代码走查与实测复验：绿灯和「结论成立」之间，没有必然关系。
自查发现 01

置信度分数从未被算法算出来

期望是过程观察面记录由算法计算得到的分数，可复现。实际是从种子文件读出的预置字面量——7 个脚本里没有任何打分或候选排序实现。该案例的「结果正确性」「执行轨迹」两项评分无效，责任层是知识与脚本，不是提示词。

自查发现 02

运行包混进了 31 处评测答案

21 处案例编号 + 10 处答案字段，分布在种子文件、6 个脚本、示例文档与决策参考里。三份隔离合同都写着「答案不得进入工作区」，但没有可复跑的检测器，合同就只是一句声明。被测系统运行时能读到答案，「100% 正确」的证据强度随之不足。

失效链 · 每一环都是「本该分开的东西被放进了同一个地方」
评审要求「GT 必须可判定」
把算法输出写死进 GT固定 A=0.82 B=0.71 Gap=0.11
运行时读到同一份文件种子文件同时装着输入与答案
判定通过过程面记「Score 计算 0.82/0.71 → Top2」
但没有实现代码里根本没有打分逻辑
修复方式
按四平面合同把期望值与答案移出运行可读路径；新增一个每次构建都跑的隔离检测器。泄漏从 31 处降到 0 处。旧结论不沿用，受影响案例在修复后的版本上复评。
06

重建隔离后重跑：评测台跑出了什么

14道题（13 道冻结 + 1 道新增）
47个场景
232条机器断言

最要紧的一条 · 已复现

一句闲聊触发了不可逆写入

生成一笔待确认记录后，用户说「最近心情不太好」。实测账本从 0 笔变成 1 笔，待确认状态被消费——一句闲聊把记录写进了账本。

根因不在「关键词匹配写松了」这一处，而是架构决定：确认路径按设计绕开模型。所以换模型、换提示词都救不了。这条已补进负例集，现在每次评测都会盯住它。

双跑对比 · 规则版 vs 模型版

模型其实很少参与判定

分桶场景数说明
两边都对31规格与实现一致
两边都缺14差距不是模型带来的，是实现本身没做
模型救回1模型版会标出总笔数
模型搞坏1模型版丢了「基于有限数据」这个限定词

模型只在 2 / 47 个场景上改变了判定——「模型参与率对结果的影响面 ≈ 4%」，第一次有了可复现的数字。

一致性检查 · 同一输入连跑三次
最终 47 个场景全稳，飘 0 个。
但第一轮飘了 1 个。查下来不是实现不稳，是断言写歪了——模型说「没办法直接恢复」，正则只认连续的「没法」。规格里明写「措辞可变，语义要是恢复不了」，这条断言本就该容许同义说法。同一输入跑 N 次，不只测模型，也测断言。
07

四个只有真跑才会知道的结论

01自我推翻

绿灯可能是假的

全 Pass 与「结论成立」之间没有必然关系。那次 12/12 全通过与「零行打分实现」，是同一次评测的两面。

02量化

模型参与率必须测出来

设计上写着「模型负责判断」，实测 16 句真实输入里只有 2 句真正调用了模型（12.5%）；双跑对比下它对结果的影响面 ≈ 4%。参与率是指标，不是设计意图。

03假失败

断言自己也会假失败

规格说「措辞可变」，断言就必须拿同义说法回归一遍。否则一次假失败会被误判成实现不稳定，然后去改本来正确的实现。

04分类

差距要分三类

实现缺失 / 实现降级 / 规格冲突。混在一起记，改造时会去修那些本来就有意为之的降级。21 条差距全部带题号与判据出处，改造优先级按投入产出排，不按严重度排。

主动洞察洞察页强调“后来怎样”，体现消费记忆的长期价值。
当前原型不等于最终运行形态Demo 仍以飞书 CUI 为主；移动端原型用于交互探索与产品化表达。

13 · 复盘

如果继续做，我会先验证三件事

把下一阶段的工作从“继续加功能”转向“验证核心价值”。

01

用户愿不愿意长期维护消费记忆？

记录有即时价值，但买后追踪属于延迟价值。需要验证用户是否愿意持续参与。

02

主动追踪是不是价值，还是打扰？

Agent 越主动不代表体验越好，需要验证相关性、时机与频率之间的平衡。

03

用户是否真的认同“消费记忆”？

最终要证明产品不是“更聪明的记账工具”，而是一套值得长期留下来的个人消费记忆系统。
